=== Front18 Security Integration Changelog ===

= 1.3.0 =
* Selecao de midia no WordPress: nova aba "Selecao de Midia" no painel do plugin, com uma grade
  que le a sua propria Biblioteca de Midia (miniaturas, busca por nome, filtro por data de
  publicacao e por pasta mes/ano, "selecionar todas do filtro"). A escolha do que e protegido
  passa a ser feita dentro do wp-admin — as imagens nao saem do seu servidor. Antes essa
  listagem era o painel Front18 fazendo proxy de centenas de imagens, o que pesava e estourava
  timeout em bibliotecas grandes.
* Ao salvar, a selecao e empurrada para o Front18 (sync reverso, autenticado pelo webhook_secret,
  nunca pela api_key publica) e aplicada no site na hora. O gerenciador de midia do painel Front18
  vira espelho somente-leitura para o site: um dono logico por site, sem as duas telas gravando a
  mesma lista. Degrada com seguranca — se o SaaS ainda nao expoe o endpoint, a selecao fica salva
  localmente e o painel avisa que nao publicou, sem quebrar nada.
* Painel repaginado em abas (Conexao, Protecao, Selecao de Midia, Avancado) — mesma informacao,
  organizada por tarefa. A aba inicial e Conexao numa instalacao nova e Protecao num site ja ativo.

= 1.2.2 =
* Cache: ao receber uma sincronizacao (/sync), o plugin passa a purgar automaticamente os
  caches de pagina inteira mais comuns (LiteSpeed, WP Rocket, W3 Total Cache, WP Super Cache,
  SG Optimizer, Cache Enabler, Nginx Helper, Autoptimize; object cache do core tambem). Cada
  purga e defensiva: so dispara se o plugin/host correspondente existir. Motivo, medido em
  producao (mclass.bulafacil.com): com LiteSpeed em HIT, o visitante recebia a home em cache de
  ANTES do Front18 estar ativo — sem o SDK injetado — e nada era protegido, mesmo com a config
  correta. O SDK e injetado server-side; um cache de pagina inteira congelava o HTML sem ele.
  Agora toda mudanca de config limpa o cache e a pagina volta a ser renderizada com a protecao.

= 1.2.1 =
* API REST: GET /media aceita filtro por data de publicacao (date_from/date_to sobre o
  post_date do anexo), aplicado tanto na grade paginada quanto no modo ids_only ("Selecionar
  todas"), para os dois casarem. O item ja retornava o campo `date`. Pareado com o painel SaaS,
  que ganha selecao por periodo alem de pasta (mes/ano). Retrocompativel: sem os parametros, o
  comportamento e o de antes.
* Admin: a tela passa a dizer em portugues claro O QUE O VISITANTE VE, combinando o modo e o
  protection_scope (que nao aparecia) — "Todas as midias ficam borradas" x "Apenas as N
  selecionadas" x "A pagina inteira fica bloqueada". Ganha o botao "Ver como visitante" com o
  aviso de que so uma janela anonima mostra o efeito: quem ja verificou a idade neste navegador
  ve tudo liberado, e era isso que fazia parecer que "nada acontecia" no teste.

= 1.2.0 =
* SEGURANCA: a api_key deixa de poder alterar as regras de protecao. Ela e publica — sai
  impressa no HTML de toda pagina protegida, porque o SDK precisa dela — e o check_permission
  a aceitava como Bearer enquanto o webhook_secret nao chegasse. Nessa janela, qualquer pessoa
  que lesse o codigo-fonte do site podia chamar /sync e (a) zerar as regras, desligando o gate
  de idade, e (b) gravar um webhook_secret proprio, tomando o canal de configuracao de forma
  permanente. O modo bootstrap continua existindo, senao o primeiro sync nunca chegaria, mas
  agora aceita EXCLUSIVAMENTE a entrega do webhook_secret e ignora qualquer regra no mesmo
  payload. O SaaS reenvia a sincronizacao com o segredo logo em seguida.
* Correcao de release: o update.json apontava 1.1.8 enquanto o plugin ja era 1.1.9. O
  auto-update nunca oferecia a versao corrente. As tres fontes de versao (cabecalho do plugin,
  constante FRONT18_VERSION e manifesto) passam a ser conferidas por teste.
* UX: emojis removidos do painel e da documentacao. Os indicadores de status continuam
  legiveis — a cor ja carregava o mesmo significado.
* Testes: nova suite (tests/wp/ no repositorio do SaaS) com 25 verificacoes sobre autenticacao
  do canal, bootstrap, sanitizacao do payload de sync e o que o /ping publico expoe.

= 1.1.2 =
* Feature: novo endpoint público GET /wp-json/front18/v1/ping — health-check para o SaaS confirmar que o plugin está instalado e ativo.
* O /ping retorna: version, status (ok / degraded / disabled), enabled, synced e last_sync.
* status 'ok' = plugin ativo e API Key configurada.
* status 'degraded' = plugin ativo mas sem API Key (aguardando configuração inicial).
* status 'disabled' = plugin instalado mas desativado no painel WordPress.
* UX: seção de Shortcodes no painel admin reescrita com linguagem mais didática e badges por perfil de uso.
* UX: Painel de Desenvolvedor renomeado para "Configurações Avançadas" com avisos sobre uso em produção.

= 1.1.1 =
* Hotfix: substitui placeholder %i do $wpdb->prepare() por interpolação direta — corrige Fatal Error em WordPress < 6.2.
* O placeholder %i para nomes de tabela foi introduzido apenas no WordPress 6.2 (maio 2023). Sites em versões anteriores recebiam um erro fatal ao ativar o plugin após a atualização 1.1.0.

= 1.1.0 =
* Segurança: hash_equals() na verificação da API Key — previne timing attacks.
* Segurança: $wpdb->prepare() em todas as queries diretas na classe API.
* Segurança: uninstall.php atualizado para limpar todas as opções das versões 1.0.x e 1.1.0.
* Segurança: $wpdb->prepare() na query de limpeza de postmeta no uninstall.
* Performance: get_option() centralizado em propriedades com cache na classe Frontend (0 chamadas duplicadas).
* Performance: update_option() removido da _calculate_scope() — migração de dados legados movida para hook de ativação/atualização.
* Performance: Ghost Tracker agora usa cache via transient de 12h (invalidado automaticamente no webhook do SaaS).
* Ghost Tracker v3: detecta imagens em ACF, WooCommerce (product galleries), Divi e theme_mods além do Elementor.
* Ghost Tracker v3: queries em lotes de 50 registros (batch) para controle de memória em sites grandes.
* API REST: filtros ricos de mídia — tipo MIME, dimensões mínimas/máximas, campo de ordenação, direção.
* API REST: metadados ricos no retorno — filesize, width, height, alt text, mime_type, is_ghost.
* API REST: novo endpoint GET /wp-json/front18/v1/media/types — lista tipos MIME disponíveis no site.
* API REST: args declarativos em todos os endpoints (auto-documentação e validação antecipada de parâmetros).
* Admin: card "Proteção Ativa Agora" — resumo visual de modo, nível, quantidade de mídias e escopo.
* Admin: seção "Shortcodes Disponíveis" — documenta [front18], [front18_lock] e data-front18="locked".
* Admin: meta box mostra status atual da proteção da página considerando regras globais e de CPT.
* Cache buster do SDK agora gerado via PHP com gmdate('Ymd') — consistente em ambientes multi-servidor.
* Testado até WordPress 6.7.
